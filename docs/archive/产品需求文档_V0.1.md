# Markdown 驱动的智能 GTD 工作空间

## 产品需求文档（PRD）

**版本：** V0.1

**文档状态：** 初稿，待确认

**产品形态：** 微信小程序为主要入口，后端提供 Markdown 工作空间、AI 整理和检索能力

**核心定位：** 将录音、文字和微信内容中的非结构化信息，整理为结构化 Task，并自动归入合适的 Markdown 任务组、文件夹和关系网络。

---

# 1. 产品概述

## 1.1 产品定位

本产品是一个以 Markdown 文件为核心数据载体的智能 GTD 工作空间。

用户可以将工作中产生的文字、录音和微信聊天内容快速投入 Inbox，由 AI 判断其中包含的是一个 Task、多个 Task、一个任务组，还是对已有 Markdown 文件的补充。系统在用户确认后，自动新建、追加或更新 Markdown 文件，并为其中的 Task 设置时间、Deadline、负责人、标签、状态和关联关系。

产品不采用固定的“项目—任务—子任务”三级结构作为唯一组织方式，而是采用以下组合：

```text
Workspace
└── Folder
    └── Folder
        └── Markdown Task Group
            ├── Task
            ├── Task
            └── Task
```

其中：

- **Task** 是最小可执行单元。
- **Markdown 文件**是多个 Task 组成的任务组或工作单元。
- **Folder** 是用户自由定义的组织容器。
- **Link** 用于表达文件和 Task 之间的跨层级关系。
- **Inbox Capture** 是尚未整理的原始输入。

## 1.2 核心价值

1. 降低任务记录成本：用户不需要先选择项目、标签、时间和文件位置。
2. 保留完整上下文：原始输入、AI 转写、任务属性、文件正文和关系都可以保存。
3. 组织方式灵活：项目、客户、问题、领域、时间和执行场景可以自由组合。
4. 方便 AI 处理：Markdown 具有清晰文本结构，便于检索、归类、总结和关系分析。
5. 保持数据开放：Markdown 文件可以导出、同步、迁移和人工编辑。
6. 支持从简单任务逐步发展为完整工作单元和知识记录。

## 1.3 产品原则

### 原则一：快速收集优先

用户首先记录，不要求立即完成归类和属性填写。

### 原则二：AI 建议，用户确认

AI 可以识别、提取、推荐和生成变更，但默认不能静默修改用户文件。

### 原则三：Markdown 是长期事实来源

结构化数据库主要用于索引和查询加速，Markdown 文件保留完整内容和关系。

### 原则四：树状组织与网状关联并存

文件夹负责归属和组织，Markdown 链接负责跨文件关系，二者不混为一谈。

### 原则五：不强制定死项目层级

文件夹和任务组可以代表项目、问题、客户、主题、时间或任意用户自定义集合。

# 2. 用户与使用场景

## 2.1 目标用户

### 第一阶段用户

- 需要管理大量工作事项的个人用户
- 使用微信记录工作内容的知识工作者
- 需要管理方案、客户、项目和跟进事项的售前、产品、项目和管理人员
- 已经使用或愿意使用 Markdown、Obsidian、Git 等工具的用户

### 后续用户

- 小型团队
- 企业项目团队
- 需要将会议、沟通和工作任务统一管理的组织

## 2.2 主要场景

### 场景一：快速记录一项任务

用户输入：

> 明天下午给李总发合同。

系统识别：

```text
Task：给李总发合同
执行时间：明天下午
负责人：我
标签：沟通、合同
```

### 场景二：从一段文字中识别多个 Task

用户输入：

> 盛京项目这周要把技术方案补完，接口部分让技术确认，周五前发内部审核。

系统识别：

```text
Task 1：补完盛京项目技术方案
Task 2：请技术确认接口范围
Task 3：周五前发送内部审核
```

系统进一步判断：

- Task 1 和 Task 3 可以归入已有“技术方案初稿.md”。
- Task 2 可能新建“确认接口范围.md”。
- 两个文件之间建立依赖或相关关系。

### 场景三：向已有 Markdown 文件追加事项

用户输入：

> 再补充一下售后服务章节。

系统发现已有文件：

```text
数垚科技/盛京医院/方案/技术方案初稿.md
```

建议操作：

```text
向已有文件追加 Task：补充售后服务章节
```

### 场景四：录音转任务

用户录音：

> 这周先把盛京的技术方案补完，接口部分找技术确认一下，周五前发我审核。

系统流程：

```text
录音
→ 语音转文字
→ 提取多个 Task
→ 推荐 Task Group 和文件位置
→ 用户确认
→ 写入 Markdown
```

### 场景五：处理微信聊天内容

用户复制微信中的几句话并粘贴到 Inbox。

系统识别聊天内容中的：

- 任务
- 时间
- 负责人
- 项目
- 等待事项
- 需要进一步确认的信息

第一版不直接读取用户任意微信聊天记录，以复制粘贴为主要方式。后续可评估分享到小程序、企业微信机器人和其他开放能力。

# 3. 核心概念与对象模型

## 3.1 Workspace

整个用户工作空间，包含所有文件夹、Markdown 文件、Task、Capture、标签和关系。

## 3.2 Folder

文件夹是组织容器，层级由用户自由定义。

文件夹可能代表：

- 项目
- 客户
- 产品
- 工作领域
- 时间阶段
- 执行场景
- 个人自定义分类

系统不强制规定文件夹的固定类型，但可以允许用户选择可选的文件夹类型，便于展示和检索。

## 3.3 Capture

用户刚输入但尚未经过整理的原始内容。

Capture 类型：

- text
- audio
- wechat_text
- shared_content
- imported_file

Capture 状态：

- unprocessed：未处理
- processing：AI 处理中
- needs_confirmation：等待确认
- processed：已处理
- archived：已归档

Capture 必须保留原始内容，不因生成 Task 而删除。

## 3.4 Task

最小可执行单元，具有独立状态和属性。

Task 基本属性：

| 属性 | 必填 | 说明 |
|---|---:|---|
| id | 是 | 全局唯一 ID |
| title | 是 | Task 名称，应尽量使用行动动词 |
| status | 是 | 当前任务状态 |
| owner | 否 | 负责人 |
| scheduled | 否 | 计划执行时间 |
| deadline | 否 | 必须完成时间 |
| priority | 否 | 优先级 |
| location | 否 | 地点 |
| context | 否 | 执行场景 |
| tags | 否 | Task 标签 |
| parent_task | 否 | 父 Task |
| depends_on | 否 | 前置 Task |
| source | 否 | 来源 Capture |
| created_at | 是 | 创建时间 |
| updated_at | 是 | 更新时间 |
| completed_at | 否 | 完成时间 |

Task 状态建议：

```text
inbox       已收集但未澄清
next        下一步行动
active      进行中
waiting     等待他人或外部条件
scheduled   已安排时间
someday     将来/也许
blocked     被前置事项阻塞
done        已完成
cancelled   已取消
archived    已归档
```

## 3.5 Markdown Task Group

Markdown 文件是多个 Task 组成的工作单元或任务组。

Task Group 可能围绕：

- 一个具体问题
- 一个项目阶段
- 一次会议
- 一个客户事项
- 一组共同属性
- 一段输入内容产生的多个 Task
- 一组需要共同查看的行动

Task Group 本身具有独立属性，例如标题、整体状态、负责人、项目、标签、截止日期和关系。

## 3.6 Link 与 Relation

Markdown 文件之间以及 Task 之间可以建立关系。

关系类型包括：

- parent_of：父级关系
- child_of：子级关系
- depends_on：依赖
- blocks：阻塞
- related_to：相关
- derived_from：来源于
- follows：后续事项
- references：参考资料
- part_of：属于某个任务组
- duplicate_of：重复事项

# 4. 信息架构与目录模型

## 4.1 工作空间示例

```text
工作空间/
├── Inbox/
│   └── captures/
├── 工作/
│   └── 数垚科技/
│       ├── 盛京医院/
│       │   ├── 项目推进.md
│       │   ├── 方案/
│       │   │   ├── 技术方案初稿.md
│       │   │   └── 内部审核.md
│       │   ├── 技术/
│       │   │   └── 确认接口范围.md
│       │   └── 会议/
│       │       └── 院方项目沟通.md
│       ├── 产品规划/
│       └── 内部管理/
├── 个人/
├── 学习/
└── Archive/
```

## 4.2 组织原则

1. 文件夹提供主要归属和浏览路径。
2. 文件名体现任务组或工作单元的主题。
3. 文件属性保存结构化元数据。
4. Markdown 链接表达跨文件关系。
5. 一个 Task 可以属于一个主要 Task Group，同时关联其他文件。
6. 文件夹和文件不强制等同于项目。

# 5. Markdown 文件规范

## 5.1 文件总体格式

每个 Markdown 文件由两部分组成：

```text
YAML Front Matter
+
Markdown 正文
```

## 5.2 Task Group 属性头示例

```markdown
---
id: group-20260901-001
type: task-group
title: 盛京医院技术方案初稿
group_type: problem
status: active

created_at: 2026-09-01T10:30:00+08:00
updated_at: 2026-09-01T10:30:00+08:00
deadline: 2026-09-05

owner: 我
project: "[[盛京医院项目]]"
area: "[[售前方案]]"

tags:
  - 医院客户
  - 技术方案
  - 方案编写

source:
  type: voice
  ref: capture-20260901-001

related:
  - "[[项目需求确认]]"
  - "[[产品能力清单]]"
---
```

## 5.3 文件正文示例

```markdown
# 盛京医院技术方案初稿

## 工作目标

完成盛京医院项目技术方案初稿，并提交内部审核。

## Tasks

### task-001｜梳理项目建设目标

- [x] 梳理项目建设目标

### task-002｜编写总体架构

- [ ] 编写总体架构

### task-003｜补充实施计划

- [ ] 补充实施计划

### task-004｜补充售后服务

- [ ] 补充售后服务

### task-005｜发送内部审核

- [ ] 发送内部审核

## 相关关系

- 前置工作：[[项目需求确认]]
- 参考资料：[[产品能力清单]]
- 后续工作：[[技术方案内部审核]]

## 执行记录

2026-09-01：完成项目建设目标梳理。
```

## 5.4 Task 详细属性

在初期可以采用“标题 + Markdown 复选框 + 内部属性区块”的方式表达 Task：

```markdown
### task-004｜补充售后服务

```yaml
id: task-004
status: next
scheduled: 2026-09-03 14:00
deadline: 2026-09-05
owner: 我
priority: medium
tags:
  - 售后服务
  - 方案编写
depends_on:
  - task-002
```

- [ ] 补充售后服务
```

后续也可以将所有 Task 属性集中放在文件头的 `tasks` 数组中，以方便机器解析。

# 6. 核心业务流程

## 6.1 Inbox 收集流程

```text
用户打开小程序
→ 进入快速记录
→ 输入文字、录音或粘贴微信内容
→ 系统立即保存 Capture
→ Capture 进入 Inbox
```

要求：

- 输入后立即保存，不因 AI 处理失败而丢失。
- 用户可以稍后再处理。
- 原始文字和音频必须保留。
- 允许用户连续输入多条 Capture。

## 6.2 AI 解析流程

```text
Capture
→ 识别来源
→ 清洗或转写
→ 判断内容类型
→ 提取 Task
→ 识别 Task Group
→ 匹配已有文件
→ 生成变更建议
```

## 6.3 内容类型判断

AI 需要判断 Capture 属于以下哪一类：

1. 单个 Task
2. 多个独立 Task
3. 一个 Task Group
4. 对已有 Markdown 的追加内容
5. 对已有 Markdown 的更新内容
6. 一条资料或记录
7. 信息不足，需要澄清

## 6.4 目标文件判断

AI 应按照以下优先级匹配目标文件：

1. 用户明确提到的文件或链接。
2. 用户明确提到的项目、客户或主题。
3. 文件标题匹配。
4. 文件夹路径匹配。
5. 标签匹配。
6. 正文语义相似度匹配。
7. 历史任务和最近使用情况匹配。
8. 如果没有高置信目标，则建议新建文件。

## 6.5 变更动作

AI 的输出动作统一为：

```text
CREATE：新建 Markdown 文件
APPEND：向已有文件追加 Task 或正文
UPDATE：修改已有属性、Task 状态或正文
LINK：建立文件或 Task 之间的关系
MOVE：移动文件或 Task 的归属位置
SPLIT：将一个文件或输入拆分为多个 Task Group
MERGE：将多个内容合并到一个 Task Group
```

一次处理可以包含多个动作。

## 6.6 用户确认流程

AI 生成提案后，向用户展示：

```text
识别到 3 个 Task

建议追加到：
[[盛京医院技术方案初稿]]

建议新建：
[[确认接口范围]]

建议标签：
#方案编写 #医院客户 #技术确认

建议关系：
技术方案初稿 → 依赖 → 确认接口范围

[确认写入] [逐条修改] [选择其他文件] [取消]
```

只有用户确认后才执行文件变更。

## 6.7 文件写入流程

```text
用户确认
→ 校验目标文件是否存在
→ 生成文件版本快照
→ 执行 CREATE / APPEND / UPDATE / LINK
→ 更新数据库索引
→ 返回写入结果
```

所有写入需要支持撤销和版本恢复。

# 7. 功能需求

## 7.1 快速收集

### FR-001 文字输入

用户可以在 Inbox 中输入一段文字并提交。

要求：

- 支持多行文本。
- 支持粘贴微信聊天内容。
- 支持草稿自动保存。
- 提交后立即形成 Capture。
- 提交后可以选择立即整理或稍后整理。

### FR-002 录音输入

用户可以在小程序内录制语音。

要求：

- 支持开始、暂停、继续、结束录音。
- 录音结束后保存音频文件。
- 生成转写文本。
- 原始音频和转写结果同时保留。
- 语音转写失败时仍保留原始音频。

### FR-003 微信内容输入

第一版支持：

- 从微信复制文本。
- 粘贴到 Inbox。
- 对多条聊天内容进行整体分析。
- 尽量保留聊天中的时间、发送者和上下文。

后续评估：

- 分享到小程序。
- 企业微信机器人。
- 客服消息入口。
- 会话内容存档接口。

## 7.2 Inbox 管理

### FR-004 Inbox 列表

显示：

- 原始内容摘要。
- 来源类型。
- 创建时间。
- 处理状态。
- AI 处理状态。
- 是否已生成 Task。

### FR-005 Inbox 批量处理

用户可以批量选择多个 Capture，让 AI 合并分析。

典型场景：

- 一次会议产生的多条记录。
- 同一段微信对话。
- 同一项目的一批语音记录。

### FR-006 原始内容查看

用户可以查看：

- 原始文字。
- 原始音频。
- 音频转写文本。
- AI 识别结果。
- 处理历史。

## 7.3 AI 解析

### FR-007 Task 提取

AI 应识别：

- 一个 Task。
- 多个 Task。
- 父子 Task。
- 等待事项。
- 信息记录而非 Task 的内容。

### FR-008 Task 属性提取

AI 尝试提取：

- Task 名称。
- 执行时间。
- Deadline。
- 负责人。
- 项目或领域。
- 地点。
- 执行场景。
- 优先级。
- 标签。
- 前置关系。

对于无法确定的字段，应返回空值或候选值，不能无依据强行填充。

### FR-009 置信度

每个 AI 识别字段应有置信度或确认状态：

- high：高置信度，可直接展示。
- medium：需要用户确认。
- low：仅作为候选建议。

### FR-010 AI 拆解

用户可以请求 AI 将复杂 Task 拆成多个子 Task。

要求：

- 默认生成 3—7 个子 Task。
- 不覆盖原 Task。
- 用户确认后才生成。
- 子 Task 可以分别设置时间、负责人和标签。

## 7.4 Markdown 文件管理

### FR-011 新建 Markdown 文件

用户可以：

- 手动新建。
- 通过 AI 提案新建。
- 指定文件夹位置。
- 指定文件名。
- 设置文件级属性。

### FR-012 追加 Markdown 文件

用户可以将一个或多个 Task 追加到已有文件。

追加前需要显示：

- 目标文件。
- 追加位置。
- 新增内容。
- 可能产生的重复项。

### FR-013 更新 Markdown 文件

支持更新：

- 文件属性。
- Task 状态。
- Task 时间。
- Task 负责人。
- 正文。
- 文件链接。

### FR-014 文件版本与撤销

每次 AI 写入或用户重要修改都需要生成版本记录。

用户可以：

- 查看修改前后差异。
- 撤销最近一次修改。
- 恢复历史版本。

## 7.5 Task 管理

### FR-015 Task 编辑

用户可以编辑：

- 名称。
- 状态。
- 执行时间。
- Deadline。
- 负责人。
- 优先级。
- 地点。
- 执行场景。
- 标签。
- 依赖关系。

### FR-016 Task 完成

用户可以完成 Task。

完成后：

- 更新 Markdown 中的复选框。
- 更新 Task 状态为 done。
- 记录完成时间。
- 更新索引。

### FR-017 Task 延期

支持：

- 修改执行时间。
- 修改 Deadline。
- 延期原因记录。
- 查看延期历史。

### FR-018 Task 依赖

用户可以设置：

- 前置 Task。
- 阻塞关系。
- 后续 Task。
- 父 Task 和子 Task。

## 7.6 文件夹管理

### FR-019 文件夹操作

支持：

- 新建文件夹。
- 重命名文件夹。
- 移动文件夹。
- 移动 Markdown 文件。
- 删除和归档。

### FR-020 自定义层级

用户可以自由建立多层文件夹，不限制层级数量，但界面需要避免过深目录导致的操作困难。

## 7.7 标签管理

标签建议分为：

- 来源标签：录音、文字、微信。
- 项目或主题标签。
- 行动类型标签：沟通、会议、审核、方案编写等。
- 执行场景标签：电脑、电话、公司、外出等。
- 状态辅助标签。

系统支持：

- 自动生成标签。
- 用户修改标签。
- 删除标签。
- 标签合并。
- 标签筛选。
- 常用标签管理。

## 7.8 检索

### FR-021 结构化筛选

按以下条件筛选：

- 状态。
- Deadline。
- 执行时间。
- 负责人。
- 文件夹。
- Task Group。
- 标签。
- 来源类型。

### FR-022 全文检索

搜索：

- 文件标题。
- Task 名称。
- Markdown 正文。
- 原始 Capture。
- 录音转写文本。
- 标签和属性。

### FR-023 语义检索

支持自然语言检索，例如：

> 找出最近还有哪些医院方案没有发出去。

系统可以匹配：

- 医院方案。
- 待发送。
- 待审核。
- 方案未完成。
- 需要跟进。

## 7.9 GTD 视图

第一阶段提供：

- Inbox。
- 今日任务。
- 逾期任务。
- 下一步行动。
- 等待中。
- 将来/也许。
- 项目或文件夹视图。
- 标签视图。

后续提供：

- 每日回顾。
- 每周回顾。
- 没有下一步行动的 Task Group。
- 长期未处理事项。
- 阻塞关系分析。

AI 不直接输出自然语言作为唯一结果，而应返回结构化提案。

## 8.2 AI 禁止行为

- 未经确认直接覆盖原文件。
- 删除用户原始输入。
- 无依据地编造 Deadline。
- 无依据地指定负责人。
- 将低置信度归类当作确定事实。
- 因为找到相似文件就直接追加内容。
- 未提示用户就合并重复 Task。

# 13. 非功能需求

## 13.1 数据安全

- 用户工作空间必须隔离。
- 音频和 Markdown 文件需要访问控制。
- 原始微信内容不得默认公开。
- AI 调用前应明确数据处理范围。
- 提供数据导出和删除能力。
- 敏感内容需要支持脱敏或关闭外部 AI 处理。

## 13.2 稳定性

- Inbox 输入优先本地或服务端立即保存。
- AI 处理失败不能影响原始内容保存。
- 文件写入需要具备幂等性。
- 重复提交不能重复生成相同 Task。
- 文件修改需要有版本快照。

## 13.3 可迁移性

- Markdown 文件使用标准 Markdown。
- YAML 属性头使用标准 YAML。
- 文件链接使用相对路径或标准 Wiki Link，并提供转换能力。
- 支持工作空间完整导出。
- 不将关键内容锁定在专有数据库格式中。

## 13.4 性能

目标：

- Capture 保存响应时间小于 1 秒。
- 常规列表页面打开时间小于 2 秒。
- 本地或数据库索引检索小于 1 秒。
- AI 处理期间展示明确状态。
- 大型工作空间需要支持分页、增量索引和异步处理。

## 13.5 可追溯性

每一次 AI 处理和文件写入都需要记录：

- 原始 Capture。
- AI 提案。
- 用户确认时间。
- 实际变更内容。
- 操作用户。
- 版本号。

# 14. 关键风险与应对方案

## 14.1 AI 归类错误

应对：

- 展示置信度。
- 低置信度要求确认。
- 不直接覆盖文件。
- 支持撤销和版本恢复。

## 14.2 文件数量过多

应对：

- 简单 Task 默认追加到已有 Task Group。
- 只有达到独立上下文、独立负责人或独立关系时才建议新建文件。
- 提供“合并”和“拆分”操作。

## 14.3 文件结构混乱

应对：

- 保持文件夹自由，但对 Markdown 属性和 Task 属性做规范化。
- 提供结构检查。
- 提供孤立文件、失效链接和重复 Task 检查。

## 14.4 数据库与 Markdown 不一致

应对：

- Markdown 文件是事实来源。
- 文件变更后触发索引更新。
- 提供重新扫描工作空间功能。
- 支持冲突检测和恢复。

## 14.5 AI 处理成本过高

应对：

- 先使用规则提取简单时间词和明确标签。
- 只有复杂内容才调用大模型。
- 对相同内容使用缓存。
- 支持用户选择“仅提取”或“完整整理”。

## 14.6 微信平台能力限制

应对：

- MVP 采用复制粘贴。
- 分享和机器人能力单独验证。
- 不把“直接读取私人聊天记录”作为产品前提。

# 15. 待确认的产品决策

以下内容需要在进入正式设计和开发前确定：

1. 产品首要形态是否确定为微信小程序？是否需要同时提供 Web 端？
2. Markdown 文件是否完全作为主数据源？
3. Task 属性采用文件内 YAML 区块，还是集中写入文件头的 `tasks` 数组？
4. 是否允许一个 Task 同时属于多个 Task Group？
5. 文件夹是否允许继承项目、负责人和标签属性？
6. AI 对高置信度结果是否允许一键批量写入？
7. 是否需要支持多人和团队协作？
8. 负责人是否只支持个人，还是包含联系人、团队成员和外部协作人？
9. 是否需要日历同步？
10. 是否需要支持本地 Markdown 文件同步和 Git？
11. 录音转写使用何种语音识别服务？
12. AI 处理内容是否允许发送到第三方模型服务？
13. 是否需要支持图片、PDF、会议纪要等其他输入类型？
