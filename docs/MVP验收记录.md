> 本节前四小节记录当时的定位过程，其中描述的导出接口已于同日整体删除（见“处理结果”）；这些陈述只反映当时状态。

失败项：`desktop: capture, edit preview, confirm, task completion, undo, export and account isolation`，断言 `Downloaded export is incomplete: 0 bytes`。单独重跑该用例 3 次为 1 通过 2 失败，可稳定复现。

### 根因（已定位，非“原因未明”）

服务端导出包本身正常，问题在浏览器与响应头的交互：

1. 直连 `GET /api/exports/{id}/download`（Node `fetch`、Playwright `context.request`）均返回 `200`、完整 ZIP、`PK\x03\x04` 头与正确 `Content-Length`；服务端访问日志同样记录 `200 OK`。
2. 页面内 `fetch()` 同一 URL 却得到 `status 204`、`body 0`，响应头仅剩 `cache-control`、`connection: close`、`pragma`，且带 `connection: close` 的合成响应未经过服务端返回路径。
3. 对照实验（最小 `node:http` 服务 + headless Chromium）确认：**只要响应带 `Content-Disposition: attachment`，页内 `fetch()` 即得到合成的 204 空响应**；去掉该头后同一 URL 返回 200 与完整字节。该行为与响应 `Content-Type` 无关（`application/zip`、`application/octet-stream`、`text/plain` 表现一致），与 Playwright `acceptDownloads` 开关无关，在 `page.route` 介入（请求经 Playwright 代理）时消失。
4. 因此 `apps/web/src/settings.tsx` 中 `fetch(download_url)` → `response.blob()` 得到空 blob，页面再以空 blob 触发 `a[download]`，测试下载到 0 字节；`download.failure()` 为 `null`、文件名正确，故此前难以判断。

结论：这不只是测试缺陷，**该导出下载路径经由 `fetch` 在 Chromium 中实际不可用**，属真实产品缺陷。此前 09-09 记录的“服务端 ZIP 正常、原因尚未定位”与此一致，本次补齐了根因。

### 处理结果：删除导出功能（2026-09-10）

确认根因后判定该功能本身多余，已整体删除，而不是修复下载路径：

- 删除后端导出 Job、ZIP 打包、`/api/exports` 与鉴权下载接口、`ExportInput`、启动时的过期导出清理，以及 `storage`/`auth` 中的 `exports` 目录段位；
